# Hyperstar discovery follow-up

Completed locally on 11 October 2026, against completion commit `c812cd4`. This continues the completed expansion. No deployment, migration, account change, durable dispatch enablement, or broad catalog survey was performed.

## Diagnosis and implementation

There was no on-disk `AGENTS.md`; the supplied instruction to communicate in English was followed. The Hyperstar research, expansion completion report, API guide, discovery adapter and both collector callers were inspected. Existing working edits were recorded before implementation and preserved.

The nearby response schema **did not retain `data.single_super_mall`**, and candidate extraction consumed only `VENDOR` rows in `data.finalResult`. Thus a separate hint never reached home validation. Two later restrictions could also omit otherwise useful candidates: mandatory `deliveryData.detail.vendorId`, and a blanket rejection of collections above 700 rows.

The existing planner now merges and deduplicates ordinary codes and the optional hint, preserves hint title/source in private diagnostics, and gives the hint a bounded opportunity before applying the store limit. Numeric owners always come from each location-scoped home. Returned code, optional delivery-owner fields and all product/document owners must agree. Missing optional nested owner fields are accepted; missing `doesDeliver` is unknown, never positive delivery evidence. Explicit out-of-area, false delivery, `NOT_OPEN`, and non-express delivery with an explicitly null slot are excluded. `isOpen`, distance and the presence of a slot alone cannot establish delivery. Scheduled delivery with positive delivery evidence is supported.

The ordinary campaign adapter and eligibility/price/stock/provenance merge remain shared. Only the corroborated super-mall gets bounded store-category discount discovery. Categories are discovered from the production category endpoint; response links are not followed. Its distinct schema has no collection `data.id`/`data.type`. Optional response owners and product category ownership are checked, and an unhonored discount filter is rejected. A category terminal can be an empty JSON result or HTTP 204 **after** a prior reported count; completeness requires the accumulated raw rows to equal that count. Initial 204, premature empty terminals, count drift, replay and conflicting repeated tuples remain unverified or failed.

Following the user's correction, the corroborated hinted store has **no separate scope, planning-request or category/campaign page cap**. All supported campaigns precede category supplements; the same adapters enumerate them until verified exhaustion or the shared scan limit. Numeric sorting determines order, never eligibility. Ordinary discovery retains its two collection slots, 12 planning requests, 20 candidate stores and eight-page guard. Ordinary collection work is planned as each home resolves, before the deferred hinted scopes, preserving the completed expansion's admission. The entire scan still retains the originally requested 40 physical requests including authentication/retries and 20-second enrichment timeout. Actual category page size is measured rather than inferred from the requested 100. Counts above 700 do not cause automatic rejection. Observed offers survive shared-budget exhaustion with explicit incomplete coverage; unprobed scopes remain unmeasured. Unsupported page-size/count contracts are still omitted.

Source, page bounds and bounded admission are frozen in the manifest and scope hash. Both legacy and durable publication retain incomplete coverage for partial traversal, so history cannot infer disappearance from those observations. Durable partial-unit completion carries explicit `bounded_partial_scope` evidence, distinct from upstream exhaustion; private comparison reports do not call it a terminal catalog. HTTP 204 metadata is cached explicitly, preserving replay/observation time. No database migration was needed. Durable dispatch remains disabled.

The one automatic feed, 40% default, stock-backed ordinary discounts, conditional-benefit exclusions and `SNAPP_STORE_CAMPAIGNS_ENABLED` rollback remain intact. Turning that flag off uses only the existing Market Party feed. No store code, numeric vendor ID or collection ID is hardcoded in production discovery.
